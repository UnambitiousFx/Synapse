# OpenAPI

Every mapped endpoint carries `Accepts`/`Produces` metadata. At the high level it is derived from the
base class's type arguments; at the low level you declare it, because nothing about a hand-written
handler can be inferred.

## What is declared for you

| Shape | Declared automatically |
|---|---|
| `Endpoint<TRequest, TResponse>` | `Accepts<TRequest>`; `200` (or the declared status) with `TResponse`; `400` validation problem |
| `Endpoint<TRequest>` | `Accepts<TRequest>`; `204` (or the declared status), no body; `400` validation problem |
| `StreamEndpoint<TRequest, TItem>` | `Accepts<TRequest>`; `200` with `IAsyncEnumerable<TItem>` for both `application/json` and `text/event-stream`; `400` validation problem |
| `MappedEndpoint<…>` | `Accepts<THttpRequest>`; `200` (or the declared status) with `THttpResponse`; `400` validation problem |
| `RawEndpoint` | **Nothing.** Declare it yourself |

`Accepts` is skipped on verbs that carry no body (`GET`, `DELETE`, `HEAD`, `OPTIONS`, `TRACE`), so a
`GET` endpoint does not advertise a request body no such request can send.

Every one of these four tiers resolves `Accepts` from its **generated binder**, not from the tier
itself — `Endpoint<TRequest, TResponse>`, `Endpoint<TRequest>`, `StreamEndpoint<TRequest, TItem>` and
`MappedEndpoint<THttpRequest, …>` all ask their binder's `BodyKind` the same way, through the same
`DeclaredRequestBody` hook. So the row above is the JSON case; the moment the bound type is
[form-bound](../high-level/messages#forms-and-files) — on any of the four — the endpoint declares the
form content types instead, described next.

### A form-bound message's schema depends on the satellite package

A message with a form-bound property — [`[FromForm]`, or a file-typed property](../high-level/messages#forms-and-files)
— does not get an `Accepts<TRequest>`. On its own, `Synapse.Endpoints` declares both form content
types with no request schema at all:

```json title="/openapi/v1.json — a form-bound POST, core package only"
"post": {
  "requestBody": {
    "content": {
      "multipart/form-data": {},
      "application/x-www-form-urlencoded": {}
    }
  }
}
```

That is deliberate, not an oversight: a message holding an `IFormFile` has no JSON schema to
describe, so `Accepts(typeof(TRequest), …)` would hand the schema generator a type it cannot render.
Declaring the two content types is what `ConsumesMatcherPolicy` needs to answer `415` for a JSON
request rather than letting it through to a `400` — content-type negotiation and schema description
are two different jobs, and the core package only does the first one. `FormRequestMetadata.RequestType`
stays `null` for the same reason regardless of which package you reference; see
[known issue 068](https://github.com/UnambitiousFx/Synapse/blob/feat/synapse-endpoints/docs/known-issues/068-null-request-type-fails-the-whole-openapi-document.md)
for what a `null` `RequestType` does to `Microsoft.AspNetCore.OpenApi` 10.0.11 without the workaround
described below.

Add [`UnambitiousFx.Synapse.Endpoints.OpenApi`](#the-satellite-package) and the schema is populated,
field by field, from the same metadata the binder itself reads:

```json title="/openapi/v1.json — the same endpoint, with the satellite package"
"post": {
  "requestBody": {
    "required": true,
    "content": {
      "multipart/form-data": {
        "schema": {
          "type": "object",
          "properties": {
            "File": { "type": "string", "format": "binary" },
            "Caption": { "type": "string" }
          },
          "required": ["File", "Caption"]
        }
      },
      "application/x-www-form-urlencoded": {
        "schema": {
          "type": "object",
          "properties": {
            "File": { "type": "string", "format": "binary" },
            "Caption": { "type": "string" }
          },
          "required": ["File", "Caption"]
        }
      }
    }
  }
}
```

The same `OpenApiSchema` object is shared by both content-type entries in memory — an endpoint
accepting either encoding accepts the same fields in both, and building two equal schemas would
double the document for no gain — so the two blocks above are identical rather than cross-referenced.

A file part (`IFormFile`, or one element of an `IFormFile` collection) always
renders as `type: string, format: binary`, never through the response-body schema generator: it is an
interface over a buffered stream, and asking `JsonSchemaExporter` to describe it is exactly what
`RequestType` stays `null` to avoid. Every other field renders as `string` — a form value arrives as
text on the wire, so an `int`-typed field is still transmitted as `"42"`. A binder that reports
`RequestBodyKind.Form` with no described fields (a supported low-level scenario) still gets both
content types, with an empty `properties` object rather than losing the request body entirely.

The `400` is declared as `HttpValidationProblemDetails` — a problem document plus an `errors`
dictionary — because that is what a bind failure actually sends. Not a plain `ProblemDetails`.

That table is the whole of what is inferred, and it is worth reading as a list of what is *not*: the
statuses the registered `IFailureHttpMapper` writes when a dispatched message returns a failed
`Result` — the `401`, `404`, `409`, `422` or `500` — are not in it. Nothing about an endpoint's types
or its configuration says which of them its handler can reach, so
[you declare them](#declaring-the-failures-your-handler-produces).

## Declaring query, header and route parameters

None of this happens without [the satellite package](#the-satellite-package): on its own,
`Synapse.Endpoints` declares nothing about a query key, a header or a route value beyond what ASP.NET
Core's own route-template parsing infers — which, for a Synapse endpoint, is nothing at all, since
[every route maps through one untyped `HttpContext` parameter](#the-satellite-package), not a typed
method signature the framework can read parameters off. With the package added, a query-bound,
header-bound or route-bound property is declared as an `operation.parameters` entry:

```csharp title="A query-bound message, unattributed and attributed"
public sealed record SearchTasksQuery : IRequest<IReadOnlyList<TaskDto>>
{
    // Bound from ?page= by the bodyless-verb convention — no attribute needed.
    public required int Page { get; init; }

    // [FromQuery(Name = "tag")] pins the wire key explicitly. Nullable, so a request with no
    // ?tag= at all binds null rather than failing — see [Repeated keys](../high-level/messages#repeated-keys).
    [FromQuery(Name = "tag")]
    public string[]? Tags { get; init; }
}

[Get("/tasks/search")]
public sealed partial class SearchTasksEndpoint : Endpoint<SearchTasksQuery, IReadOnlyList<TaskDto>>;
```

```json title="/openapi/v1.json — GET /tasks/search"
"parameters": [
  {
    "name": "Page",
    "in": "query",
    "required": true,
    "schema": { "type": ["integer", "string"] }
  },
  {
    "name": "tag",
    "in": "query",
    "required": false,
    "schema": { "type": "array", "items": { "type": "string" } }
  }
]
```

Four rules decide what is declared, and each one exists because getting it wrong documents a
contract the endpoint does not actually have:

- **The name is the key the binder reads, not the property name.** `Page` has no `[FromQuery]`, so
  it is bound — and documented — under its own property name, `Page`, capital `P`; query binding is
  case-insensitive at runtime, so `?page=` still works even though the document says `Page`. `Tags`
  has `[FromQuery(Name = "tag")]`, so the document says `tag`, not `Tags` — the same reconciliation
  the binder itself does. A parameter name that did not match the key the binder reads would be a
  wrong document, not a stylistic choice.
- **`required` means "the binder rejects a request that omits this"**, not "the CLR type looks
  mandatory". `required: true` needs all three of: a non-nullable property, no constructor default,
  and a single-value shape — a scalar or one `IFormFile`. So `Page` above is `required: true`, and
  each of these is `required: false` even though none of them is a nullable scalar:
  - a property with a **constructor default** — `record ListUsers(int Page = 1)` — because an absent
    `?page=` falls back to `1` and answers `200`;
  - a **collection-shaped** property, `Tags` included, however it is declared: HTTP cannot express
    zero values under a key, so an absent `?tag=` binds an empty collection rather than failing.
    That holds for a non-nullable `string[]` exactly as it does for a `string[]?`;
  - a property declared C#-`required` but **nullable** — `required string? Sort` — because `required`
    is a creation-site rule the compiler enforces on the object initializer, not a statement about
    what the request must carry.

  See [Is a missing value an error?](../high-level/messages#is-a-missing-value-an-error) for the
  binding rule this declaration mirrors rather than reimplementing.
- **A `path` parameter is always `required: true`.** OpenAPI 3.x has no optional path parameter, so a
  route-bound property that the binder itself treats as optional — a `Guid? TaskId`, or a route
  property with a constructor default — is still documented as required. The alternative is not a
  more honest document but an invalid one.
- **A route parameter is reconciled with the template's inference, never duplicated.** ASP.NET Core
  infers a `path` parameter from the route template itself (`{taskId}`) independently of anything
  Synapse emits; the transformer finds that entry already present and fills in its `schema` and
  `required` rather than adding a second one. Two entries for the same path parameter is invalid
  OpenAPI, and some client generators reject it outright.

That reconciliation rule matters because a route-bound property being declared **at all** is new
behaviour this package adds, not something the framework already did for a Synapse endpoint — a
Synapse route handler is one `context => …` delegate, and the framework only infers parameters from a
method-level signature it can read types and names off. Without the satellite package, a Synapse
`{taskId}` route segment appears in `/openapi/v1.json`'s path template and nowhere else — no `schema`,
no `required`, not even a `parameters` entry:

```csharp title="A route- and header-bound message"
public sealed record GetTaskQuery : IRequest<TaskDto>
{
    public required Guid TaskId { get; init; }          // matches {taskId} in the route

    [FromHeader("X-Tenant")]
    public required string Tenant { get; init; }         // headers are never bound by convention
}

[Get("/tasks/{taskId:guid}")]
public sealed partial class GetTaskEndpoint : Endpoint<GetTaskQuery, TaskDto>;
```

```json title="/openapi/v1.json — GET /tasks/{taskId}, with the satellite package"
"parameters": [
  { "name": "taskId", "in": "path", "required": true, "schema": { "type": "string", "format": "uuid" } },
  { "name": "X-Tenant", "in": "header", "required": true, "schema": { "type": "string" } }
]
```

## The satellite package

Declaring parameters and the form schema needs `Microsoft.AspNetCore.OpenApi`'s own schema generator
— `OpenApiOperationTransformerContext.GetOrCreateSchemaAsync`, specifically, so a parameter's schema
matches how the same CLR type is described everywhere else in the document, rather than a
hand-rolled Type-to-schema table drifting out of sync with it. `Synapse.Endpoints` itself carries no
`PackageReference` at all — that is a deliberate zero, not an oversight, and pulling in
`Microsoft.AspNetCore.OpenApi` would break it for every consumer, including the ones who never
generate a document. So this work ships as its own opt-in package:

```xml title="YourApp.csproj"
<PackageReference Include="UnambitiousFx.Synapse.Endpoints.OpenApi" Version="…" />
```

```csharp title="Program.cs"
builder.Services.AddSynapseEndpointsOpenApi();
builder.Services.AddOpenApi();
```

One call, in whichever order relative to `AddOpenApi()`. It registers two things together, and
deliberately offers no way to register just one of them:

- **An operation transformer** (`ConfigureAll<OpenApiOptions>`, so it reaches every named document
  `AddOpenApi()` produces, however many) that adds the parameters and the form schema described
  above.
- **The fixup for [known issue 068](https://github.com/UnambitiousFx/Synapse/blob/feat/synapse-endpoints/docs/known-issues/068-null-request-type-fails-the-whole-openapi-document.md)** —
  without it, a form-bound endpoint crashes the *entire* document (`500` on `/openapi/v1.json`,
  every endpoint, not just the form-bound one), because `Microsoft.AspNetCore.OpenApi` 10.0.11
  cannot handle `FormRequestMetadata.RequestType` being `null`.

The two halves fail in opposite, equally unusable directions on their own: the fixup alone declares
no parameters and no form schema at all, and the transformer alone crashes the document the moment
any endpoint accepts a form body. An API that only works correctly with both halves present should
not offer a way to register just one, so there is deliberately no second call, and no
`OpenApiOptions` extension method the way every other OpenAPI declaration in this package is one —
a reader expecting that symmetry is the reason this paragraph exists.

`UnambitiousFx.Synapse.Endpoints.OpenApi` targets `net10.0` **only**. Not `net9.0`+, the way
`Synapse.Endpoints` itself is, because `GetOrCreateSchemaAsync` is new in .NET 10 — a .NET 9 host has
no equivalent call to hang the schema on, and the only alternative (a hand-rolled Type-to-schema
table) would describe a type inconsistently with the response bodies and the rest of the document
that `Microsoft.AspNetCore.OpenApi` already generates for that same host. On `net8.0`/`net9.0`, you
get [everything the core package declares on its own](#a-form-bound-messages-schema-depends-on-the-satellite-package) —
correct `Accepts`/`Produces` metadata, form content types with no schema — and nothing this package
adds.

## The declared status code follows `Configure`

A declarative success method updates the metadata as well as the behaviour:

```csharp
public override void Configure(IEndpointBuilder<TaskCreated> builder) =>
    builder.Created(created => $"/tasks/{created.TaskId}");
```

```json title="/openapi/v1.json"
"post": {
  "responses": {
    "201": { "content": { "application/json": {
               "schema": { "$ref": "#/components/schemas/TaskCreated" } } } },
    "400": { "content": { "application/problem+json": {
               "schema": { "$ref": "#/components/schemas/HttpValidationProblemDetails" } } } }
  }
}
```

A response with **no body** is declared with no content schema, which is what `NoContent()` and
`StatusCode(int)` produce:

```json
"204": { "description": "No Content" }
```

:::warning `OnSuccess` does not update the document
An `OnSuccess` override changes the response without telling the document: the declared status stays
whatever the default (or the last declarative call) was. Prefer the
[declarative vocabulary](../high-level/responses#changing-it-declaratively) where it suffices, and use
`Raw` to correct the metadata when it does not.
:::

## Declaring the failures your handler produces

`Produces`, `ProducesProblem` and `ProducesValidationProblem` are on every endpoint builder, at every
tier, and each returns its own builder type so the chain does not widen:

```csharp
public override void Configure(IEndpointBuilder<TaskDto> builder)
{
    builder.ProducesProblem(StatusCodes.Status404NotFound)     // ProblemDetails
        .ProducesProblem(StatusCodes.Status409Conflict)
        .Produces<RateLimitDto>(StatusCodes.Status429TooManyRequests)  // status + your own body
        .Produces(StatusCodes.Status304NotModified)            // status, no body
        .ProducesValidationProblem(422)                        // HttpValidationProblemDetails
        .Summary("Get a task");
}
```

```json title="/openapi/v1.json"
"get": {
  "responses": {
    "200": { "content": { "application/json": {
               "schema": { "$ref": "#/components/schemas/TaskDto" } } } },
    "400": { "content": { "application/problem+json": {
               "schema": { "$ref": "#/components/schemas/HttpValidationProblemDetails" } } } },
    "404": { "content": { "application/problem+json": {
               "schema": { "$ref": "#/components/schemas/ProblemDetails" } } } }
  }
}
```

The arity with no response declares the same things through the non-generic `IEndpointBuilder`:

```csharp
public override void Configure(IEndpointBuilder builder) =>
    builder.ProducesProblem(StatusCodes.Status404NotFound);
```

Three things worth knowing:

- These are **additive**. They do not touch the success status, which stays whatever `Configure`'s
  declarative response method set, and they do not replace the inferred `400`.
- They **describe**, they do not enforce. Declaring a `409` does not make one happen; the handler's
  `Result` and the registered `IFailureHttpMapper` decide that. Declare what your handler can
  actually reach — a status listed here that never occurs is as wrong as one that occurs and is
  missing.
- `Produces(int)` with no body is declared as `void`, so it survives into the document rather than
  being skipped for having no schema.

There is no convention that declares the mapper's whole table for you. `IFailureHttpMapper` exposes
the mapping, not the set of statuses it can produce, and it is replaceable — so any such shorthand
would be a hardcoded guess about somebody else's type.

## Declaring it at the low level

```csharp
public override void Configure(IRawEndpointBuilder builder)
{
    builder.Accepts<WebhookPayload>()
        .Produces<HealthDto>()                                        // 200 + body
        .Produces(StatusCodes.Status304NotModified)                   // status, no body
        .ProducesProblem(StatusCodes.Status409Conflict)                // status + ProblemDetails
        .ProducesValidationProblem()                                  // 400, errors dictionary
        .Tag("Ops")
        .Summary("Liveness, with an ETag");
}
```

Declaring nothing is valid and emits nothing — the route still works, it just has no documented
contract. Note `ProducesValidationProblem()`'s default of `400`: unlike the higher tiers this one
declares no `400` of its own, because nothing binds, so the default is the useful call here rather
than a duplicate.

## Adding anything else

`Raw(Action<RouteHandlerBuilder>)` reaches the underlying builder, at either level:

```csharp
builder.Raw(route => route.WithOpenApi());   // ⚠ not AOT-safe — see below
```

It is no longer the way to declare a response, though. `Raw(route => route.ProducesProblem(404))` and
`builder.ProducesProblem(404)` do the same thing, and the second says what it means without reaching
past the surface.

Under Native AOT, use a transformer instead. There are two, and which one you want depends on
whether you are changing one route or the whole document:

```csharp title="One route — the direct replacement for WithOpenApi"
builder.Raw(route => route.AddOpenApiOperationTransformer((operation, context, ct) =>
{
    operation.Deprecated = true;
    return Task.CompletedTask;
}));
```

```csharp title="Every route — on the options, in Program.cs"
builder.Services.AddOpenApi(options =>
{
    options.AddOperationTransformer((operation, context, ct) =>
    {
        operation.Extensions["x-generated-by"] = new OpenApiAny("Synapse.Endpoints");
        return Task.CompletedTask;
    });
});
```

## APIs this library steers you away from

A few standard ASP.NET Core OpenAPI/routing APIs are unavailable under Native AOT, and are
deliberately never used by this library's own implementation:

| API | Why it is unavailable |
|---|---|
| `WithOpenApi` | `[RequiresDynamicCode]` + `[RequiresUnreferencedCode]`, and `[Obsolete("ASPDEPR002")]` as of .NET 10. Use `AddOpenApiOperationTransformer` on the route instead — see [above](#adding-anything-else) |
| `TypedResults.CreatedAtRoute` / `AcceptedAtRoute` / `RedirectToRoute` | `[RequiresUnreferencedCode]` |

`IEndpointBuilder<TResponse>.Created(...)` compiles down to `TypedResults.Created`, deliberately not
`TypedResults.CreatedAtRoute` — so using the declarative response vocabulary keeps you off the
hazardous path by construction, without having to know these attributes exist.

## `net8.0` has no document integration

`Synapse.Endpoints` targets `net8.0;net9.0;net10.0`, but `Microsoft.AspNetCore.OpenApi` — the package
that generates `/openapi/v1.json` — is `net9.0`+ only.

On `net8.0` you still get accurate `Accepts`/`Produces` metadata on every mapped route, and nothing
about request handling or routing is degraded. You just get no generated OpenAPI document to serve.

## Serving the document

```csharp
builder.Services.AddOpenApi();
…
app.MapOpenApi();          // GET /openapi/v1.json
```

Under Native AOT, every type reachable from the document must be registered on a
`JsonSerializerContext` — including some the diagnostics cannot see for you. That is the subject of
[Native AOT](./native-aot), which is worth reading before you publish rather than after.
