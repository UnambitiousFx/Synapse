# Diagnostics

The bundled analyzer reports these at build time. Errors stop the build; warnings and info do not.

| ID | Severity | Fires when | Fix |
|---|---|---|---|
| `SYNE001` | Error | A route template parameter has no matching bindable property | Add a property with that name, or rename the route parameter |
| `SYNE002` | Error | Two properties resolve to the same route parameter, query key, or form field, or more than one carries an explicit `[FromBody]` | Rename one, give it a distinct `[FromRoute]`/`[FromQuery]`/`[FromForm]` name, or keep only one `[FromBody]` |
| `SYNE003` | Info | A `POST`/`PUT` endpoint returning a value declares no explicit success mapping, so it always responds `200 OK` | Call `Created`/`Accepted`/etc. in `Configure`, or override `OnSuccess`, to make the status explicit |
| `SYNE004` | Warning | `OnSuccess` is overridden *and* `Configure` calls a declarative success method | Remove one — the declarative call always wins, so the override is dead code |
| `SYNE005` | Error | The bound message implements `IStreamRequest<T>` but the endpoint derives from `Endpoint<...>` | Derive from `StreamEndpoint<...>` instead |
| `SYNE006` | Error | `[InGroup<T>]`'s `T` does not derive from `EndpointGroup` | Make `T` a subclass of `EndpointGroup` — in practice the compiler's `CS0311` reports this first, since `InGroupAttribute<TGroup>` is itself constrained to `where TGroup : EndpointGroup, new()`; do not expect to actually see `SYNE006` fire |
| `SYNE007` | Warning | An explicit `[FromBody]` property is declared on a bodyless verb (`GET`/`DELETE`/`HEAD`/`OPTIONS`/`TRACE`), so it can never bind | Remove `[FromBody]`, change the verb, or accept the property will always be missing |
| `SYNE008` | Warning | A request/response type is not registered in any `JsonSerializerContext` found in the compilation. For a low-level endpoint, also the type argument of a `BodyAsync<T>` read or an `Accepts<T>`/`Produces<T>` declaration | Add `[JsonSerializable(typeof(...))]` for it — see [Native AOT](./native-aot); only reported once your app has at least one `JsonSerializerContext` at all |
| `SYNE009` | Error | A route is declared both by attribute and by a verb call in `Configure` | Remove one — only one may declare the route |
| `SYNE010` | Error | The endpoint class is generic, nested inside a generic type, or has no public parameterless constructor | Make it a top-level, non-generic class with a public parameterless constructor — `MapEndpoint<TEndpoint>()` requires `TEndpoint : EndpointBase, new()`. An `abstract` endpoint class never fires this: discovery skips abstract classes outright, so an abstract intermediate base shared by several endpoints is a supported pattern |
| `SYNE011` | Error | A route/query/header-bound property has no accessible setter and its type is not a record | Add a setter, or make the type a record so the value can be applied through `with` |
| `SYNE012` | Error | A non-string, non-enum route/query/header-bound property binds a value of a type with neither public static `TryParse(string, out T)` nor `TryParse(string, IFormatProvider, out T)` — for a supported collection shape (`T[]`, `List<T>`, `IReadOnlyList<T>`, `IEnumerable<T>`), this names the *element* type `T`, not the collection type | Add either overload to that type — implementing `IParsable<T>` supplies the second — or change the property's (or element's) type |
| `SYNE014` | Warning | An endpoint declares its route in `Configure` (so no verb is visible at compile time) and at least one property's binding source came from convention rather than an explicit `[From*]` attribute | Annotate those properties with `[FromRoute]`/`[FromQuery]`/`[FromHeader]`/`[FromBody]`, or declare the route with a route attribute — see [Escape hatches](./escape-hatches). Harmless for a computed `GET`; a real bug for a computed `POST` |
| `SYNE015` | Warning | A `[NotBound]` property sits on a message the binder deserializes from the request body (a body-carrying verb, or an explicit `[FromBody]` on a bodyless one), so a caller can still set it by naming it in the payload | Add `[JsonIgnore]` beside `[NotBound]`, and have whatever owns the value assign it unconditionally rather than only when it is still at its default — see [Messages & binding](../high-level/messages). `[NotBound]` alone is sufficient on a bodyless verb |
| `SYNE016` | Error | A route/query/header-bound property is enumerable but not one of the four collection shapes the binder supports (`HashSet<T>`, `Dictionary<K,V>`, etc.) | Change the property's type to `T[]`, `List<T>`, `IReadOnlyList<T>`, or `IEnumerable<T>`. A jagged array (`T[][]`) is *not* caught here — Roslyn's array rank reflects only the outermost dimension, so it reads as a supported `T[]` shape whose element type is `T[]`, and is reported as `SYNE012` naming that element instead |
| `SYNE017` | Warning | A property binds from the request form — via `[FromForm]`, or because its type is a file (`IFormFile`, etc.) with no attribute at all — on a bodyless verb (`GET`/`DELETE`/`HEAD`/`OPTIONS`/`TRACE`), so it can never bind | Remove `[FromForm]` or the file typing, change the verb, or accept the property will always be missing |
| `SYNE018` | Error | One message has both form-bound properties and body-bound properties. A request is either multipart form or JSON, never both, so whichever the binder reads, the other group can never bind | Move the body-bound properties to `[FromForm]`, or split them onto a request that does not also bind from the form |
| `SYNE019` | Info | A message became form-bound purely by inference — an `IFormFile`-typed property with no `[FromForm]` anywhere on the message — and at least one other property followed it to the form as a result | Add `[FromForm]` to the file property to state the intent explicitly, which silences this; the endpoint itself is already correct |
| `SYNE020` | Error | The endpoint class — or a type enclosing it — is not declared `partial`, so the generator has nowhere to emit the binding | Declare the named type `partial`. Reported per type missing the keyword, so a nested endpoint's error names the type to actually fix — see [Shape requirements](./base-classes#shape-requirements) |
| `SYNE021` | Error | A tier whose binding is generated (`Endpoint<…>`, `StreamEndpoint<…>`, `MappedEndpoint<…>`, `SelfHandledEndpoint<…>`) also declares `BindAsync` by hand | Remove the hand-written `BindAsync` — it collides with the generated one as `CS0111` — or derive from `RawEndpoint<…>` to write the binding by hand instead |

## Grouped by what they are about

**Binding** — `SYNE001`, `SYNE002`, `SYNE007`, `SYNE011`, `SYNE012`, `SYNE014`, `SYNE015`, `SYNE016`, `SYNE017`, `SYNE018`, `SYNE019`, `SYNE021`
See [Messages & binding](../high-level/messages).

**Responses** — `SYNE003`, `SYNE004`
See [Responses](../high-level/responses).

**Shape of the endpoint class** — `SYNE005`, `SYNE006`, `SYNE009`, `SYNE010`, `SYNE020`
See [Base classes](./base-classes).

**Native AOT** — `SYNE008`
See [Native AOT](./native-aot), which also documents its four blind spots.

## Two you should not expect to see

`SYNE006` (an `[InGroup<T>]` whose `T` is not an `EndpointGroup`) is essentially unreachable:
`InGroupAttribute<TGroup>` is itself constrained to `where TGroup : EndpointGroup, new()`, so the
compiler reports `CS0311` first. If you never see `SYNE006`, that is expected.

`SYNE010` never fires for an `abstract` endpoint class — discovery skips abstract classes outright, so
an abstract intermediate base shared by several endpoints is a supported pattern rather than a
violation.

## Which diagnostics apply at which level

A low-level endpoint binds nothing, so the binding diagnostics have nothing to check. They are
suppressed by kind rather than reported and ignored:

| Level | Applies | Suppressed |
|---|---|---|
| `Endpoint<…>`, `StreamEndpoint<…>`, `MappedEndpoint<…>` | All of them | — |
| `RawEndpoint<TRequest>` / `RawEndpoint<TRequest, TResponse>` | `SYNE003`, `SYNE004`, `SYNE005`, `SYNE008`, `SYNE009`, `SYNE010` | `SYNE001`, `SYNE002`, `SYNE007`, `SYNE011`, `SYNE012`, `SYNE014`, `SYNE015`, `SYNE016`, `SYNE017`, `SYNE018`, `SYNE019`, `SYNE020`, `SYNE021` |
| `RawEndpoint` | `SYNE008` (call sites), `SYNE009`, `SYNE010` | Everything else |
