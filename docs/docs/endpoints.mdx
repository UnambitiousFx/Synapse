# Endpoints

`UnambitiousFx.Synapse.Endpoints` maps an HTTP route directly onto a command or query: one
attribute plus one class declaration, no method body, for the common case. It sits on top of
`IHttpInvoker` (see [ASP.NET Core Integration](./aspnetcore)) — the invoker still does the
dispatch and failure mapping, this package removes the boilerplate around calling it. This is the
recommended default for a new HTTP surface; reach for a hand-written `IHttpInvoker` lambda only
when an endpoint's shape genuinely does not fit here.

## Why

Every route in a hand-written Minimal API surface repeats the same shape: read the inputs, build a
message, call the invoker, map the success response.

```csharp title="before"
tasks.MapGet("/{id:guid}", async (
        [FromRoute] Guid id,
        [FromServices] IHttpInvoker invoker,
        CancellationToken ct) =>
    await invoker.InvokeAsync(new GetTaskQuery { TaskId = id }, ct))
    .WithName("GetTask")
    .WithSummary("Get a task by ID");
```

```csharp title="after"
[Get("/tasks/{taskId:guid}")]
public sealed class GetTaskEndpoint : Endpoint<GetTaskQuery, TaskDto>;
```

Binding, dispatch and response mapping are generated at compile time. Status code and response
shape stay fully controllable — declaratively for the common shapes, imperatively (`OnSuccess`,
`Raw`) for the rest.

## Your first endpoint

```csharp
public sealed record ListTasksQuery : IRequest<IReadOnlyList<TaskDto>>;

[Get("/tasks")]
public sealed class ListTasksEndpoint : Endpoint<ListTasksQuery, IReadOnlyList<TaskDto>>;
```

No `Configure`, no `OnSuccess`, no constructor. `ListTasksQuery` is dispatched through
`IInvoker` exactly as if you had called `invoker.InvokeAsync(new ListTasksQuery(), ct)` yourself;
the response is written as `200 OK` with the value as the JSON body.

Wire every generated endpoint group into the route table with one line per assembly:

```csharp
// Program.cs
app.MapSynapseEndpoints(new SynapseEndpointGroup());
```

`SynapseEndpointGroup` is the class the generator emits — one per assembly, containing one
`endpoints.MapEndpoint<T>()` call per discovered endpoint. It is named `SynapseEndpointGroup`
rather than `EndpointGroup` so it never collides with the `EndpointGroup` base class you derive
groups from (see [Groups](#groups) below). `MapSynapseEndpoints` also walks the resulting route
table once, after every group has mapped, and throws if two endpoints claim the same HTTP method
and route.

You can also map a single endpoint by hand — `endpoints.MapEndpoint<GetTaskEndpoint>()` — which is
exactly what the generated group does for every endpoint it finds; mapping by hand and mapping
through a generated group behave identically.

## The four base classes

| Base class | Response | Reach for it when |
|---|---|---|
| `Endpoint<TRequest>` | `204 No Content` by default | The message is `IRequest` (no response) — a delete, a fire-and-forget command |
| `Endpoint<TRequest, TResponse>` | `200 OK` with the response body by default | The message is `IRequest<TResponse>` and the wire contract can be the message itself — the common case |
| `StreamEndpoint<TRequest, TItem>` | Negotiated on `Accept` — see [Streaming](#streaming) | The message is `IStreamRequest<TItem>` |
| `MappedEndpoint<THttpRequest, TRequest, TResponse, THttpResponse>` | `200 OK` with `THttpResponse` by default | The public HTTP contract must not be the same shape as the internal CQRS message |

All four are stateless singletons: one instance is created at startup, `Configure` runs once
against it, and the same instance serves every request. Constructor injection is therefore
unavailable by design — pull whatever you need from the `HttpContext` passed to `OnSuccess`
instead.

Prefer `Endpoint<TRequest, TResponse>` over `MappedEndpoint<...>` unless the wire contract
genuinely must differ from the internal message: the mapped variant is a deliberate opt-in that
costs two extra mapping methods (`ToRequest`, `ToResponse`) per endpoint.

```csharp
public sealed class CreateThingEndpoint
    : MappedEndpoint<CreateThingRequestDto, CreateThingCommand, int, CreateThingResponseDto>
{
    public override CreateThingCommand ToRequest(CreateThingRequestDto request) =>
        new(request.Name);

    public override CreateThingResponseDto ToResponse(int response) =>
        new(response.ToString());

    public override void Configure(IEndpointBuilder<CreateThingResponseDto> builder) =>
        builder.Created(value => $"/things/{value.Id}");
}
```

## Binding

A message's properties are matched against the route, the query string, headers and the request
body by five rules, applied in order — the first one that applies wins:

| # | Rule |
|---|---|
| 1 | `[NotBound]` excludes the property entirely, regardless of anything else |
| 2 | `[FromRoute]` / `[FromQuery]` / `[FromHeader]` / `[FromBody]` pins the source explicitly, with the key taken from the attribute's name or else the property name |
| 3 | A name matching a route template parameter (case-insensitively) binds from the route |
| 4 | On a bodyless verb (`GET` / `DELETE` / `HEAD` / `OPTIONS` / `TRACE`), an unmatched property binds from the query string. An endpoint that declares its route in `Configure` has no verb the generator can see, so it is assumed bodyless too — see [Escape hatches](#escape-hatches) |
| 5 | Otherwise, the property binds from the request body |

**Headers are never bound by convention** — rule 3 only matches route parameters, and rule 5
falls through to the body, never to a header. `[FromHeader]` is the only way to read one:

```csharp
public sealed record PatchThingCommand : IRequest
{
    public Guid ThingId { get; init; }

    [FromHeader("If-Match")]
    public string? ETag { get; init; }
}
```

Exclude a value a pipeline behaviour or handler sets internally with `[NotBound]`, so a caller
cannot supply it by guessing the property name:

```csharp
public sealed record CreateThingCommand : IRequest<Guid>
{
    public required string Title { get; init; }

    [NotBound]
    public string? ModifiedBy { get; init; }
}
```

### The record-or-setter rule

A property bound from the route, query string or a header must be assignable after the message
already exists — the generated binder either calls a setter directly, or applies the value
through a `with` expression, which only a `record` supports. A property that is neither on a
record nor has an accessible setter is reported as **SYNE011** and omitted from the generated
code (it does not stop the build, but the value is never bound). This restriction applies only to
route/query/header-bound properties — a `[FromBody]` property is populated by deserializing the
whole message in one JSON read, so neither a setter nor `SYNE011` applies to it.

### `required` does not work here

A route/query/header-bound property on a message with a parameterless constructor cannot be
`required`, because the binder constructs the message with a bare `new T()` and applies the bound
value afterwards through a `with` expression — a call site that, by the language's own rules,
cannot satisfy a `required` member. `examples/EndpointsApi`'s `GetTaskQuery` documents this
directly:

```csharp
/// <remarks>
///     <see cref="TaskId" /> is deliberately not <c>required</c>: the generated binder for a
///     route-only message constructs it with a bare <c>new GetTaskQuery()</c> and then applies the
///     bound value via a <c>with</c> expression — a call site that cannot satisfy a <c>required</c>
///     member, so marking a purely route/query/header-bound property <c>required</c> fails to
///     compile against the current generator output.
/// </remarks>
public sealed record GetTaskQuery : IRequest<TaskDto>
{
    public Guid TaskId { get; init; }
}
```

### Prefer a positional record

Give a bound message a positional constructor instead of init-only properties where you can:

```csharp
public sealed record GetTaskQuery(Guid TaskId) : IRequest<TaskDto>;
```

This is a genuine improvement, not just style, for two independent reasons:

1. **It sidesteps the `required` limitation entirely.** A type with no parameterless constructor
   (a positional record's only constructor takes its parameters) is constructed by the generated
   binder through a direct call to that constructor — computing and validating each bound
   argument first, then calling `new GetTaskQuery(taskId)` once — rather than `new T()` followed by
   a `with` expression. There is no post-construction assignment step for `required` to conflict
   with.
2. **It allocates once instead of twice.** The init-only path benchmarked in
   `benchmarks/SynapseBenchmark/EndpointDispatchBenchmark.cs` — a route-only query with a
   parameterless constructor — does `new GetThingQuery()` followed by
   `message = message with { Id = valueId }`: two record allocations. That extra allocation is the
   entire ~1.4% (~130 B/request) gap the benchmark measured between the generated endpoint and an
   equivalent hand-written Minimal API lambda; everything else about the two paths was
   latency-indistinguishable. A positional record's single constructor call removes it.

## Responses

`Endpoint<TRequest>` defaults to `204 No Content`; `Endpoint<TRequest, TResponse>` and
`MappedEndpoint<...>` default to `200 OK` with the response serialized as the body. Override the
default declaratively in `Configure`:

```csharp
public override void Configure(IEndpointBuilder<TaskCreated> builder)
{
    builder.Created(created => $"/tasks/{created.TaskId}")
        .Summary("Create a task");
}
```

| Method | Response |
|---|---|
| `Ok()` | `200 OK` with the response body (the default) |
| `Created(location)` | `201 Created`, the response as the body, `Location` built from the response |
| `Accepted(location?)` | `202 Accepted`, optionally with a `Location` header |
| `NoContent()` | `204 No Content` |
| `StatusCode(code)` | A fixed status code, no body |

Prefer these over overriding `OnSuccess` where they suffice: a declarative call also updates the
OpenAPI metadata the endpoint reports (`ProducesResponseMetadata` picks up the declared status
code), where an `OnSuccess` override does not. `Created(...)` is written in terms of
`TypedResults.Created`, deliberately not `TypedResults.CreatedAtRoute` — see
[Native AOT](#native-aot) for why that distinction matters.

Override `OnSuccess` for anything the declarative vocabulary cannot express — it receives the
response and the `HttpContext` and returns any `IResult`. If both are used on the same endpoint,
the declarative call always wins (`SYNE004` warns about this).

**Failures are untouched by any of this.** A bind failure (missing/unparsable route, query or
header value) short-circuits to `400` with a `ProblemDetails` body before the message is even
dispatched. A dispatch failure — the handler itself returning a failed `Result` — flows through
the same `IFailureHttpMapper` registered for `IHttpInvoker` (see
[Failure mapping](./aspnetcore#failure-mapping--ifailurehttpmapper)), completely unchanged by this
package.

## Groups

Give a set of endpoints a shared route prefix, tags or authorization policy with an
`EndpointGroup`:

```csharp
public sealed class TasksGroup : EndpointGroup
{
    public override void Configure(IEndpointGroupBuilder builder)
    {
        builder.Prefix("/tasks").Tag("Tasks");
    }
}
```

```csharp
[Get("/")]
[InGroup<TasksGroup>]
public sealed class ListTasksEndpoint : Endpoint<ListTasksQuery, IReadOnlyList<TaskDto>>;
```

`ListTasksEndpoint`'s own route (`/`) combines with the group's prefix (`/tasks`) to serve
`GET /tasks`. `IEndpointGroupBuilder` also has `RequireAuthorization(...)` and `Raw(...)` — an
escape hatch onto the underlying `RouteGroupBuilder`.

`[InGroup<TGroup>]`'s type parameter is constrained to `where TGroup : EndpointGroup, new()`, so
**`SYNE006` (an `InGroup<T>` whose `T` does not derive from `EndpointGroup`) can essentially never
fire** — the compiler reports `CS0311` first, before the analyzer even runs. If you never see
`SYNE006` reported, that is expected; it is not a sign the check is broken.

## Streaming

`StreamEndpoint<TRequest, TItem>` streams the items of an `IStreamRequest<TItem>`. The response
format is negotiated on the `Accept` header: a value containing `text/event-stream` yields
server-sent events, and anything else (including a missing header) yields a JSON array written
incrementally as items arrive — matching `IHttpInvoker.InvokeStreamAsync`, failed items are
silently skipped.

```csharp
[Get("/stream")]
[InGroup<TasksGroup>]
public sealed class StreamTasksEndpoint : StreamEndpoint<StreamTasksQuery, TaskDto>;
```

See [Native AOT](#native-aot) below for a Native-AOT-specific gotcha this base class introduces.

## Escape hatches

`Raw(Action<RouteHandlerBuilder>)` reaches the underlying `RouteHandlerBuilder` directly, for
filters, rate limiting, output caching, versioning or anything else the fluent surface does not
wrap:

```csharp
public override void Configure(IEndpointBuilder<string> builder)
{
    builder.Raw(route => route.RequireRateLimiting("fixed"));
}
```

An endpoint whose route must be computed rather than declared as a constant can omit the route
attribute entirely and declare it in `Configure` instead:

```csharp
public sealed class ComputedEndpoint : Endpoint<ComputedQuery, string>
{
    public override void Configure(IEndpointBuilder<string> builder)
    {
        var suffix = Environment.GetEnvironmentVariable("ROUTE_SUFFIX") ?? "default";
        builder.Get($"/computed/{suffix}");
    }
}
```

Declaring the route both ways — a route attribute **and** a verb call on `Configure`'s builder —
is reported as `SYNE009`; only one may declare it.

There is one thing to know about this shape. The route's verb is a runtime value, so the generator
cannot see it — and it needs a verb to decide whether an unannotated property binds from the query
string (rule 4) or from the request body (rule 5). It **assumes a bodyless verb**, which is right for
the computed `GET` this escape hatch is nearly always used for, and wrong for a computed `POST`,
where the properties would bind from the query string instead of the body. `SYNE014` warns whenever
any property's source actually came from that assumption, so a computed `POST` is told rather than
silently mis-bound. Pin those properties with `[FromBody]` (or the other `[From*]` attributes) and
the warning goes away along with the ambiguity:

```csharp
public sealed record ComputedCommand : IRequest<string>
{
    // Explicit, so the assumed verb cannot get it wrong — and SYNE014 stays silent.
    [FromBody] public required string Payload { get; init; }
}
```

## Diagnostics reference

| ID | Severity | Fires when | Fix |
|---|---|---|---|
| `SYNE001` | Error | A route template parameter has no matching bindable property | Add a property with that name, or rename the route parameter |
| `SYNE002` | Error | Two properties resolve to the same route parameter, the same query key, or more than one carries an explicit `[FromBody]` | Rename one, give it a distinct `[FromRoute]`/`[FromQuery]` name, or keep only one `[FromBody]` |
| `SYNE003` | Info | A `POST`/`PUT` endpoint returning a value declares no explicit success mapping, so it always responds `200 OK` | Call `Created`/`Accepted`/etc. in `Configure`, or override `OnSuccess`, to make the status explicit |
| `SYNE004` | Warning | `OnSuccess` is overridden *and* `Configure` calls a declarative success method | Remove one — the declarative call always wins, so the override is dead code |
| `SYNE005` | Error | The bound message implements `IStreamRequest<T>` but the endpoint derives from `Endpoint<...>` | Derive from `StreamEndpoint<...>` instead |
| `SYNE006` | Error | `[InGroup<T>]`'s `T` does not derive from `EndpointGroup` | Make `T` a subclass of `EndpointGroup` — in practice the compiler's `CS0311` reports this first, since `InGroupAttribute<TGroup>` is itself constrained to `where TGroup : EndpointGroup, new()`; do not expect to actually see `SYNE006` fire |
| `SYNE007` | Warning | An explicit `[FromBody]` property is declared on a bodyless verb (`GET`/`DELETE`/`HEAD`/`OPTIONS`/`TRACE`), so it can never bind | Remove `[FromBody]`, change the verb, or accept the property will always be missing |
| `SYNE008` | Warning | A request/response type is not registered in any `JsonSerializerContext` found in the compilation | Add `[JsonSerializable(typeof(...))]` for it — see [Native AOT](#native-aot); only reported once your app has at least one `JsonSerializerContext` at all |
| `SYNE009` | Error | A route is declared both by attribute and by a verb call in `Configure` | Remove one — only one may declare the route |
| `SYNE010` | Error | The endpoint class is generic, nested inside a generic type, or has no public parameterless constructor | Make it a top-level, non-generic class with a public parameterless constructor — `MapEndpoint<TEndpoint>()` requires `TEndpoint : EndpointBase, new()` |
| `SYNE011` | Error | A route/query/header-bound property has no accessible setter and its type is not a record | Add a setter, or make the type a record so the value can be applied through `with` |
| `SYNE012` | Error | A non-string, non-enum route/query/header-bound property's type has no public static `TryParse(string, out T)` | Add a `TryParse` method to the type, or change the property's type |
| `SYNE013` | Warning | A message type is bound by two or more endpoints whose *resolved* bindings differ (different route/verb produced different bindable properties) | Give each endpoint its own message type — only one endpoint's binding resolution is baked into the single shared binder; **this diagnostic warns, it does not fix anything** — every other endpoint sharing the type keeps binding incorrectly at runtime |
| `SYNE014` | Warning | An endpoint declares its route in `Configure` (so no verb is visible at compile time) and at least one property's binding source came from convention rather than an explicit `[From*]` attribute | Annotate those properties with `[FromRoute]`/`[FromQuery]`/`[FromHeader]`/`[FromBody]`, or declare the route with a route attribute — see [Escape hatches](#escape-hatches). Harmless for a computed `GET`; a real bug for a computed `POST` |

`SYNE013` is a real, standing limitation of the current design: `EndpointRegistry.RegisterBinder`
is keyed by message type, so exactly one binder is ever generated per type — built from whichever
endpoint sorts first ordinally by fully-qualified name — regardless of how many endpoints share
that message. Give a shared type identical routes and verbs (so the resolved bindings are actually
identical) and this is harmless; give it different ones and only the first endpoint's resolution
is correct.

## Native AOT

This is the section most likely to save you a bad afternoon. Every item below was found the hard
way during implementation — several as a `500` on `/openapi/v1.json` or on first request, with the
build itself staying green and warning-free.

### Register every reachable type

Every type reachable from an endpoint's response **or from the OpenAPI document** must be in your
`JsonSerializerContext`, or the app throws
`NotSupportedException: JsonTypeInfo metadata for type 'X' was not provided by TypeInfoResolverChain`
at runtime, on the first request that touches it — with no build warning to catch it first, unless
`SYNE008` happens to cover that exact type (see below).

```csharp
[JsonSerializable(typeof(TaskDto))]
[JsonSerializable(typeof(IReadOnlyList<TaskDto>))]
[JsonSerializable(typeof(IAsyncEnumerable<TaskDto>))]
[JsonSerializable(typeof(TaskCreated))]
[JsonSerializable(typeof(CreateTaskCommand))]
// ...
[JsonSerializable(typeof(ProblemDetails))]
[JsonSerializable(typeof(HttpValidationProblemDetails))]
internal sealed partial class AppJsonSerializerContext : JsonSerializerContext;
```

`SYNE008` catches most of this — it flags a request or response type that is used by an endpoint
but missing from every `JsonSerializerContext` it can find — but it has three deliberate gaps you
need to cover yourself:

- **`ProblemDetails` and `HttpValidationProblemDetails`.** `SYNE008` checks only the endpoint's own
  declared request/response type, not every type reachable from the failure/error pipeline or the
  OpenAPI document — its own descriptor documents this exclusion explicitly. Both types are
  genuinely needed at runtime (error responses, the OpenAPI schema), so register them yourself;
  nothing else will remind you.
- **A `StreamEndpoint<TRequest, TItem>`'s wire type is `IAsyncEnumerable<TItem>`, not bare
  `TItem`.** That is the exact type `StreamEndpoint.CreateDescriptor` declares via
  `ProducesResponseMetadata` and the type `Microsoft.AspNetCore.OpenApi` asks the resolver chain
  for when building the schema for a streamed route. Registering only `TItem` leaves the build
  green — `SYNE008` does not flag this gap — but `/openapi/v1.json` throws
  `JsonTypeInfo metadata for type 'IAsyncEnumerable<TaskDto>' was not provided` at request time.
  Register the `IAsyncEnumerable<TItem>` closed type as well.
- **A custom `TypeInfoResolverChain` entry that is not itself a `JsonSerializerContext`** is
  invisible to `SYNE008` entirely.

### Consuming by `ProjectReference` needs its own analyzer reference

The NuGet package bundles the analyzer with `PrivateAssets="all"` on its own reference to the
generator project — which is exactly what keeps the generator from becoming a transitive
*build* dependency of your project when you add the package normally. That same setting means the
analyzer does **not** flow to a project that references `Synapse.Endpoints` via `ProjectReference`
instead of the NuGet package (a multi-repo or monorepo setup, for instance). Add the generator as
your own analyzer reference in that case:

```xml
<ProjectReference Include="...\Synapse.Endpoints.Generator.csproj"
                  OutputItemType="Analyzer" ReferenceOutputAssembly="false" />
```

Without it, every `EndpointRegistry.GetBinder<T>()` / `GetMetadata<T>()` call throws at startup
with a message pointing at exactly this.

### APIs this library steers you away from

A few standard ASP.NET Core OpenAPI/routing APIs are unavailable under Native AOT and are
deliberately never used by this library's own implementation:

| API | Why it's unavailable |
|---|---|
| `WithOpenApi` | `[RequiresDynamicCode]` + `[RequiresUnreferencedCode]`, and `[Obsolete("ASPDEPR002")]` as of .NET 10. Use `AddOpenApiOperationTransformer` instead |
| `TypedResults.CreatedAtRoute` / `AcceptedAtRoute` / `RedirectToRoute` | `[RequiresUnreferencedCode]` |

`IEndpointBuilder<TResponse>.Created(...)` compiles down to `TypedResults.Created`, deliberately
not `TypedResults.CreatedAtRoute` — so using the declarative response vocabulary keeps you off the
hazardous path by construction, without you having to know these attributes exist.

### `net8.0` has no OpenAPI document integration

`Synapse.Endpoints` targets `net8.0;net9.0;net10.0`, but `Microsoft.AspNetCore.OpenApi` — the
package that generates the `/openapi/v1.json` document — is `net9.0`+ only. On `net8.0` you still
get accurate `Accepts`/`Produces` metadata on every mapped route (nothing about request handling or
routing is degraded), you just get no generated OpenAPI document to serve.

## Attribute collisions

The verb attributes (`[Get]`, `[Post]`, `[Put]`, `[Patch]`, `[Delete]`) are named differently from
`Microsoft.AspNetCore.Mvc`'s `[HttpGet]`/`[HttpPost]`/... family, so they do not actually collide
with it — both `using` directives can coexist in the same file without ambiguity.

`[FromHeader]` is where a real collision happens: `Microsoft.AspNetCore.Mvc` has its own
`FromHeaderAttribute`, and importing both `Microsoft.AspNetCore.Mvc` and
`UnambitiousFx.Synapse.Endpoints` in the same file makes `[FromHeader]` ambiguous
(`CS0104: 'FromHeader' is an ambiguous reference between ...`) — for instance in a project that
mixes MVC controllers with Synapse endpoints. Resolve it with a `using` alias — **alias the full
type name, not the short attribute form**; aliasing just `FromHeader` still leaves `[FromHeader]`
ambiguous, because attribute-name lookup also tries the `...Attribute`-suffixed form, which the
`Microsoft.AspNetCore.Mvc` import still supplies:

```csharp
// Works: aliases the exact name the ambiguity is over.
using FromHeaderAttribute = UnambitiousFx.Synapse.Endpoints.FromHeaderAttribute;

// Does NOT work: [FromHeader] is still CS1614-ambiguous, because the Mvc import still
// resolves the "...Attribute"-suffixed form that attribute lookup also tries.
using FromHeader = UnambitiousFx.Synapse.Endpoints.FromHeaderAttribute;
```

Uncommon HTTP verbs that have no dedicated attribute (`HEAD`, `OPTIONS`, ...) use
`[HttpEndpoint(method, route)]` instead of a verb-specific attribute — unrelated to the collision
above, but the other reason you might reach for it:

```csharp
[HttpEndpoint("HEAD", "/tasks")]
public sealed class HeadTasksEndpoint : Endpoint<ListTasksQuery, IReadOnlyList<TaskDto>>;
```
